# DE001: Repeated failed logons

**Status:** experimental lab rule. **Priority:** medium.

## Detection hypothesis
Five failures for the same host, account domain, user and source IP in an inclusive rolling 300-second window. Alert on crossing the threshold; rearm after the window falls below five.

## Telemetry
Windows Security event **4625**, provider `Microsoft-Windows-Security-Auditing`. See [field mapping](../schema.md). Audit configuration and collector coverage must be verified before deployment.

## Investigation
Confirm status/substatus and logon type in the original event. Correlate successful logons and source ownership. Check lockouts and whether the account is privileged.

Preserve event record IDs, source host, timestamps and original records. Document the disposition as authorized activity, suspicious activity, or insufficient evidence. Containment requires the organization's incident-response process; this lab takes no response actions.

## False positives and tuning
Stale service credentials, a user retrying an old password, or a broken scheduled task.

Baseline the affected host role and actor. Any exception should have an owner, narrow scope, ticket and expiry. The reference evaluator deliberately applies no hidden allowlists.

## Blind spots
Does not detect low-and-slow guessing, distributed sources, or password spraying across many users. Missing source IP/domain/user prevents a match.

## Validation
See the named positive and negative scenarios in `data/scenarios.json`. Benign lookalikes that should still alert are documented in the validation report. Synthetic test success is not a production accuracy measurement.

## Reference
[T1110.001 — MITRE ATT&CK](https://attack.mitre.org/techniques/T1110/001/). Mapping describes a possible behavior, not a conclusion about attacker intent.
